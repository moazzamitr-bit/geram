# راهنمای انتقال به سرور اصلی

این سند برای کسی است که می‌خواهد گرم را روی سرور اصلی بالا بیاورد. دو راه دارید: **Vercel** (همین الان) یا **سرور خودتان با Docker**.

---

## ۱. قبل از هر چیز: کدام حالت؟

| حالت | یعنی | برای چه؟ |
|---|---|---|
| `SANDBOX` | کد ورود ثابت `123456`، واریز شبیه‌سازی | دمو و تست |
| `CLOSED_BETA` | کاربر واقعی، پیامک واقعی، بدون واریز شبیه‌سازی | تست با تعداد محدود کاربر واقعی |
| `PRODUCTION` | مثل بتا + منبع قیمت تأییدشده | فقط بعد از درگاه پرداخت، احراز هویت و مجوز |

> تا وقتی درگاه بانکی و تسویه واقعی وصل نشده، روی **CLOSED_BETA** بمانید. با پول واقعی کاربر عمومی کار نکنید.

## ۲. متغیرهای لازم

همه در `.env.example` با توضیح آمده‌اند. حداقل‌ها:

| متغیر | از کجا | ضروری برای |
|---|---|---|
| `GERAM_EXECUTION_MODE` | خودتان: `SANDBOX` یا `CLOSED_BETA` | همه چیز |
| `NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_ANON_KEY` | Supabase → Settings → API | ورود |
| `SUPABASE_SERVICE_ROLE_KEY` | Supabase → Settings → API (service_role) | پیامک، پنل ادمین، کرون |
| `DATABASE_URL` | Supabase → دکمه Connect → Connection string (Session pooler) | خرید و فروش |
| `KAVENEGAR_API_KEY` / `KAVENEGAR_OTP_TEMPLATE` | پنل کاوه‌نگار (قالب verify با یک `%token%`) | پیامک واقعی (بتا و بعد) |
| `OTP_HASH_SECRET` / `CRON_SECRET` | یک رشته تصادفی ۳۲+ کاراکتری | امنیت کد ورود و کرون |

## ۳. دیتابیس

همه مایگریشن‌های `supabase/migrations` باید روی دیتابیس اجرا شده باشند. تا `20261021130000` اجرا شده است؛ `20261021140000_auth_otp.sql` برای پیامک لازم است.

## ۴. موجودی اولیه خزانه (مهم)

بدون این مرحله **هر خریدی رد می‌شود**، چون پلتفرم فلزی برای فروش ندارد.

1. پنل ادمین ← «شارژ و موجودی» ← «ثبت موجودی اولیه خزانه»
2. فلز و مقداری که **واقعاً** در اختیار شرکت است (گرم) + مدرک را ثبت کنید. برای فروش مشتری، «نقدینگی عملیاتی» (تومان) هم ثبت کنید.
3. همان ادمین با «ثبت در دفترکل» ژورنال را همان لحظه می‌نویسد. ادمین دیگری لازم نیست. تکرار همان درخواست موجودی را دوباره زیاد نمی‌کند.

## ۵. اجرا روی سرور خودتان (Docker)

```bash
docker build \
  --build-arg NEXT_PUBLIC_SUPABASE_URL=... \
  --build-arg NEXT_PUBLIC_SUPABASE_ANON_KEY=... \
  -t geram .
docker run -d --restart unless-stopped --env-file .env.production -p 3000:3000 geram
```

- جلوی آن Nginx یا Caddy با HTTPS بگذارید (هدر HSTS فعال است).
- سلامت: `GET /api/health` باید `200` بدهد.
- وضعیت پیکربندی: `GET /api/core/readiness` — باید `databaseBacked: true` و `phoneAuthReady: true` باشد.
- کرون روزانه: `curl -H "Authorization: Bearer $CRON_SECRET" https://YOUR_DOMAIN/api/cron/revenue`
- محدودیت نرخ درخواست در حافظه همان سرور است؛ با یک کانتینر دقیق کار می‌کند.

## ۵٫۱ ورود (رمز عبور، نه پیامک)

پیش‌فرض `AUTH_METHOD=password` است. صفحه `/auth/login` همان اول فرم شماره و رمز عبور را نشان می‌دهد و `/api/auth/phone-login` پاسخ `method_disabled` می‌دهد. پیامک فقط با `AUTH_METHOD=otp` فعال می‌شود (sms.ir یا کاوه‌نگار). ثبت‌نام به `SUPABASE_SERVICE_ROLE_KEY` نیاز دارد. ورود ادمین با ایمیل حسابی است که `profiles.role = admin` دارد؛ `admin@geram.ir` روی سرور خودمیزبان فعلی این نقش را ندارد.

پروکسی `/sb` اگر همین الان GoTrue را جواب می‌دهد، برای این اصلاح لازم نیست عوض شود. فقط `Set-Cookie` را حذف نکنید و `NEXT_PUBLIC_SUPABASE_URL` همان آدرسی بماند که مرورگر می‌بیند (`https://geram.co/sb`). متغیر `GERAM_EXECUTION_MODE` را برای این تغییر عوض نکنید.

## ۵٫۲ شبکه داکر و آدرس داخلی سوپابیس

کانتینر اپ در `deploy/docker-compose.yml` همزمان به شبکه خودش (`deploy_default`) و شبکه خارجی `supabase_default` وصل است. بدون این اتصال، بعد از هر بار ساخته‌شدن کانتینر، نام `supabase-db` از داخل اپ حل نمی‌شود.

درخواست‌های سمت سرور (ورود با رمز، ورود ادمین، و بقیه کلاینت‌های سرور سوپابیس) اگر به آدرس عمومی `https://دامنه/sb` بروند، از CDN آروان برمی‌گردند و کند یا قطع می‌شوند. برای اینکه سرور مستقیم به درگاه API روی همان ماشین برسد، این خط را به `/opt/geram/.env.production` اضافه کنید و کانتینر اپ را دوباره بالا بیاورید:

```
SUPABASE_INTERNAL_URL=http://supabase-envoy:8000
```

این آدرس ریشه درگاه است و پسوند `/sb` ندارد؛ Caddy همان پیشوند را قبل از فرستادن به پورت ۸۰۰۰ برمی‌دارد. در Compose فعلی سوپابیس، کانتینر درگاه `supabase-envoy` است و روی شبکه `supabase_default` با نام‌های `kong` و `envoy` هم جواب می‌دهد. اگر هنوز درگاه قدیمی Kong را دارید و `supabase-envoy` حل نشد، به‌جای آن `http://kong:8000` بگذارید.

اگر این متغیر نباشد یا خالی باشد، سرور همان `NEXT_PUBLIC_SUPABASE_URL` را صدا می‌زند و سایت مثل قبل کار می‌کند. مرورگر همیشه آدرس عمومی را می‌بیند. این مقدار آرگومان بیلد نیست؛ فقط هنگام اجرای کانتینر خوانده می‌شود. کوکی نشست همچنان با نام میزبان عمومی ساخته می‌شود تا میان‌افزار و مرورگر یک نشست را ببینند.

## ۶. چک‌لیست قبل از باز کردن برای کاربر

- [ ] `/api/core/readiness`: `databaseBacked: true`، `phoneAuthReady: true`
- [ ] ورود با پیامک واقعی روی یک شماره تست
- [ ] موجودی اولیه توسط همان ادمین در دفترکل ثبت شده
- [ ] یک خرید و فروش کوچک واقعی (۱۰۰ هزار تومانی) از کیف پول تست
- [ ] سوئیچ توقف معامله در پنل ادمین را یک بار خاموش/روشن کنید و ببینید خرید رد می‌شود
- [ ] اطلاعات تماس (`lib/data.ts` → `contactInfo`) با اطلاعات واقعی شرکت جایگزین شده
- [ ] یک ادمین ساخته شده (`deploy/create-admin.sh`)

## ۷. هنوز آماده نیست (قبل از PRODUCTION)

درگاه پرداخت و واریز واقعی، برداشت پایا/ساتنا، احراز هویت شاهکار، قرارداد تأمین‌کننده/خزانه، منبع قیمت قابل اجرا (به‌جای TGJU)، و مجوز فعالیت.
